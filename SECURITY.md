# 🔒 Политика безопасности и Спецификация криптографии (Security Specification)

Команда **Obxodka** со всей ответственностью относится к безопасности пользователей, шифрованию трафика и защите персональных данных. Данный документ подробно описывает используемые криптографические протоколы, принципы **Zero-Trust / Zero-Log** и процесс сообщения об уязвимостях.

---

## 🛡️ Криптографический стек и протоколы

| Уровень защиты | Технология / Алгоритм | Описание и назначение |
| :--- | :--- | :--- |
| **Аутентификация (mTLS)** | **ECDSA NIST P-256 / RSA 4096** | Двусторонняя взаимная аутентификация клиента и сервера. Каждое устройство получает уникальный динамический `.pfx` сертификат. |
| **Public Key Pinning** | **SPKI SHA-256 Hash** | Клиент сверяет SHA-256 хэш открытого ключа сервера с эталонным (`AppSecrets.SslPublicKeyHash`), исключая атаки типа Man-In-The-Middle (MITM). |
| **Симметричный шифр** | **AES-256-GCM (AEAD)** | Промышленный стандарт блочного шифрования с аутентификацией данных (128-битный GCM Tag). |
| **Вектор инициализации (IV)** | **96-bit Monotonic Nonce** | Уникальный атомарный счётчик (`Interlocked.Increment`) + `SessionId`. 100% защита от атак повторного использования Nonce. |
| **Транспортный уровень** | **TLS 1.3 / gRPC HTTP/2** | Инкапсуляция пакетов Layer 3 в защищенные стримы через порт **443 TCP**. |
| **Упреждающая коррекция** | **FEC Engine (4:1 XOR Shards)** | Мгновенное восстановление 1 потерянного пакета из 4 без ожидания повторной передачи (Zero RTT loss recovery). |
| **Хранилище на клиенте** | **Windows DPAPI / Android Keystore** | Аппаратная защита JWT-токенов и сессионных сертификатов в изолированном хранилище ОС (`SecureStorage`). |

## 🔐 Zero-Trust & Zero-Log Архитектура

Архитектура Obxodka построена на строгом разделении данных:

```
+------------------------------------+------------------------------------+
| ДАННЫЕ В СЕРВЕРНОЙ БД (POSTGRESQL) |    ДАННЫЕ В RAM (ZERO-LOG ПОЛИТИКА)|
+------------------------------------+------------------------------------+
|  Email и хэш пароля (PBKDF2)       |  IP-адреса посещаемых сайтов (НЕТ) |
|  Баланс времени подписки           |  DNS-запросы и домены (НЕТ)        |
|  Общий объем использованных байт   |  Тела сетевых пакетов (НЕТ)        |
|  Отпечаток mTLS сертификата        |  История интернет-активности (НЕТ) |
+------------------------------------+------------------------------------+
```

1. **Эфемерная память:** Обработка пакетов в ядре ноды выполняется исключительно в оперативной памяти через `ArrayPool<byte>.Shared`. Сразу после передачи в сетевой интерфейс память освобождается и перезаписывается.
2. **Отсутствие дисковых логов:** На серверах полностью отключено логирование сетевых потоков (PCAP / NetFlow / DNS Query Logs).

## 🚨 Как сообщить об уязвимости (Responsible Disclosure)

Если вы обнаружили потенциальную уязвимость в безопасности или баг в криптографической подсистеме Obxodka:

> [!IMPORTANT]
> **Пожалуйста, НЕ создавайте публичные тикеты (Issues) с описанием уязвимости.**

1. Отправьте подробный технический отчёт на адрес команды безопасности:  
   📧 **contact@octocore.dev**

2. Включите в письмо:
   * Подробное описание уязвимости и потенциальный вектор атаки
   * Шаги для воспроизведения или Proof of Concept (PoC)
   * Версию приложения и затронутую платформу (Windows / Android / Linux Node)
   * Ваши контакты для координации

### Наше обязательство:
* Подтверждение получения отчёта в течение **48 часов**.
* Оперативное расследование и информирование о ходе устранения.
* По вашему желанию — публикация вашего имени в списке благодарностей проекта (Security Hall of Fame).
