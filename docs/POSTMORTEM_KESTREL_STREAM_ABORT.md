**Дата инцидента:** 15 октября 2026 г.

## 1. Контекст и масштаб проблемы

На протяжении более чем 6 месяцев разработка VPN-клиента сталкивалась с периодически возникающим и трудноуловимым сбоем у пользователей в Российской Федерации:
1. Клиент инициировал подключение, проходил TLS-рукопожатие, но затем туннель зависал на стадии обмена трафиком.
2. В логах клиента стабильно возникала ошибка:
   `InvalidOperationException: Сервер не отвечает на тестовые пакеты (отправлено 1764 Б, получено 0 Б)`.
3. Соединение принудительно разрывалось самим клиентом, чтобы предотвратить перехват маршрутов по умолчанию мертвым адаптером.

Из-за специфики региона (блокировки ТСПУ РКН, активный DPI, сбросы TCP-соединений с зарубежными IP) подозрение всегда падало на внешние факторы:
* «Глушилки» и сигнатурные блокировки ТСПУ;
* Блокировка SNI-доменов (Cloudflare, Speedtest и др.);
* Подозрение на сбросы ClientHello по отпечаткам пакетов.

## 2. Прорыв в расследовании (15 октября 2026 г.)

При детальном анализе боевого журнала `debug.html`, полученного с реального пользовательского ПК в РФ при подключении к серверу в Стокгольме (`<master-node>`), было обнаружено поразительное несоответствие:

1. **Обход DPI сработал безупречно:**
   * Кандидат `login.live.com` установил TCP-соединение за **52 мс**;
   * Микросегментация ClientHello (129 Б + 317 Б) прошла ТСПУ без единой задержки;
   * Сертификат сервера был успешно проверен по открытому ключу (`xZIbvT6/B+...`);
   * **Оба луча HTTP/2** (`Ray #0` на порту 443 и `Ray #1` на порту 8443) получили **HTTP 200 OK** и назначили IP `100.64.0.9`.

2. **Затем наступала тишина:**
   * Клиент настраивал адаптер Wintun через `netsh` (занимает 2.6 секунды);
   * Запускался зонд `VerifyDownlinkAsync`, отправлявший 31 цикл пингов (1764 Б);
   * За 12 секунд от сервера не пришло **ни единого байта** (`RX=0`), и клиент уничтожал сессию.

## 4. Корневая причина (Root Cause)

Виновником оказался стандартный защитный механизм веб-сервера **ASP.NET Core Kestrel**:
`KestrelServerLimits.MinRequestBodyDataRate`

По умолчанию Kestrel требует, чтобы входящее тело HTTP-запроса передавалось со скоростью не менее **240 байт в секунду** с льготным периодом (Grace Period) в **5 секунд**.

### Цепочка событий катастрофы:
```
[Клиент подключается] (HTTP/2 POST /api/v1/sync)
       │
       ├──> [Сервер отвечает 200 OK + HandshakeResponse]
       │
       ├──> [Клиент выполняет netsh: IP, MTU, DNS] (длится 2.6 секунды)
       │    (в туннель уходят только редкие пинги по 11 байт: скорость << 240 Б/с)
       │
       ├──> [Проходит ровно 5.0 секунд льготного периода Kestrel]
       │    Kestrel решает: "Это Slowloris-атака!"
       │    Kestrel: "The request stream was aborted." -> шлет TCP RST в Caddy!
       │
       ├──> [Caddy закрывает сессию: "connection reset by peer"]
       │
       └──> [Клиент завершает netsh, шлет 31 пинг в уже мертвый сокет]
            (TX=1764, RX=0 -> Клиент: "Сервер не отвечает!" -> Самосброс)
```

Тесты в Узбекистане (`LiveStreamEchoTestAsync`) всегда проходили, потому что юнит-тест не создавал виртуальный адаптер Wintun и не запускал `netsh`: он слал пинг через 20 мс и завершался за 800 мс, не дожидаясь 5-секундного таймера Kestrel.

## 5. Внесенные исправления

### 5.1. Серверная часть (`obxodka.Octopus`)
В `Program.cs` Kestrel настроен на режим непрерывного двунаправленного стриминга:
```csharp
builder.WebHost.ConfigureKestrel(kestrel =>
{
    kestrel.Limits.MaxRequestBodySize = null;
    kestrel.Limits.MinRequestBodyDataRate = null;   // Отключен 5-секундный лимит скорости
    kestrel.Limits.MinResponseDataRate = null;      // Отключен лимит скорости ответа
    kestrel.Limits.RequestHeadersTimeout = TimeSpan.FromMinutes(10);
    kestrel.Limits.Http2.InitialConnectionWindowSize = 8388608;
    kestrel.Limits.Http2.InitialStreamWindowSize = 4194304;
    kestrel.Limits.Http2.MaxFrameSize = 65536;
    kestrel.Limits.Http2.KeepAlivePingDelay = Timeout.InfiniteTimeSpan;
    kestrel.Limits.Http2.KeepAlivePingTimeout = Timeout.InfiniteTimeSpan;
    kestrel.Limits.Http3.MaxRequestHeaderFieldSize = 65536;
    ...
});
```
В `ObxodkaTunnelEndpoint.cs` инактивити-таймаут сокета увеличен с 15 до 90 секунд. Контейнер пересобран и развернут на боевом сервере Швеции (`vpn2`).

### 5.2. Клиентская часть (`WindowsVpnService.cs`)
1. **Устранено самоуничтожение:** Если дуплексный канал HTTP 200 установлен и исходящие пакеты уходят (`TX > 0`), отсутствие немедленного ответа от синтетического зонда больше не выбрасывает `InvalidOperationException`. Клиент переходит к установке маршрутов и запуску `ProcessTrafficAsync`.
2. **Оптимизация пула Reality SNI (`AppSecrets.cs`):** Домен `login.live.com`, показавший пробитие ТСПУ за 52 мс, перемещен на первое место в списке `AllowedSniPool`.
3. **Сокращение таймаута зондирования:** Время ожидания первоначального зонда уменьшено с 12 до 6 секунд для ускорения поднятия туннеля.
